You are building "RoomieMatch" — a web-based roommate matching and
accommodation search platform for a Nigerian polytechnic ND final

PROJECT GOAL
-------------
A platform where a user can (a) list an accommodation/room they're
offering, (b) search accommodation listings by location, price and
amenities, and (c) get a ranked list of compatible prospective
roommates computed from a weighted lifestyle-compatibility algorithm —
covering both "I have a room, need a roommate" and "I need a room and
a roommate" scenarios, including partial and group-based matching.

CORE FEATURES — COVER EVERY SCENARIO BELOW
----------------------------------------------

1. AUTHENTICATION & PROFILE
   - Register/login, bcrypt password hashing, email verification
     (Brevo)
   - A user can be a pure seeker, pure lister, or BOTH at once (e.g.
     someone who already has a room and is looking to fill it AND is
     also open to moving elsewhere) — role is not exclusive
   - Full lifestyle-preference profile form (all fields in schema
     above); flag and visually warn the user if their profile is
     incomplete, since incomplete profiles reduce match accuracy
   - "Matching status" toggle: actively_looking / paused /
     found_roommate — paused/found_roommate users are excluded from
     other users' match results (scenario: someone already matched
     shouldn't keep appearing to others)

2. ACCOMMODATION LISTING (for listers)
   - Create/edit/remove listing with photos (Supabase Storage),
     amenities checklist, price, room type, available-from date
   - Mark listing status: active / filled / expired / removed
   - Listings auto-expire after a configurable period (e.g. 60 days)
     if not renewed — background/cron check, or checked lazily on
     fetch (scenario: stale listings cluttering search results)
   - A listing can already have existing occupants (currentOccupants)
     — when a listing has occupants, roommate compatibility must be
     computed against the AVERAGE/aggregate lifestyle profile of all
     current occupants, not just the lister (scenario: joining a
     3-person flat, not a 1-on-1 match)
   - Lister can require listing verification (upload proof of
     ownership/tenancy) — verified listings show a badge; unverified
     ones are still visible but flagged (scenario: reduce scam risk
     without blocking genuine new listers who lack documents yet)

3. IMAGE UPLOAD (Cloudinary) — profile photos and listing photos
   - Use the `cloudinary/cloudinary_php` SDK on the backend; uploads
     are SIGNED (never expose the API secret to the browser) — the
     frontend sends the file to your PHP endpoint, PHP uploads it to
     Cloudinary server-side, then stores the returned secure_url +
     public_id on the user/listing document
   - Folder structure in Cloudinary: `roomiematch/profiles/{userId}`
     and `roomiematch/listings/{listingId}`, so assets are easy to
     find/audit and to bulk-delete if a user or listing is removed
   - On upload, apply a Cloudinary transformation to auto-generate a
     compressed, size-capped version (e.g. `w_1200,h_1200,c_limit,
     q_auto,f_auto`) so users can't dump multi-MB originals that slow
     down page loads
   - Generate a separate thumbnail transformation URL on the fly for
     grid/list views (e.g. `w_300,h_300,c_fill,q_auto,f_auto`) rather
     than storing a second physical file — Cloudinary derives this
     from the same public_id at request time
   - Enforce on the backend (not just the frontend `accept` attribute):
     file type whitelist (jpg, png, webp), max file size (e.g. 5MB),
     and a max photo count per listing (e.g. 8) — reject anything
     outside these limits with a clear error before calling Cloudinary
   - When a user replaces their profile photo or a lister removes a
     listing photo, delete the old asset from Cloudinary via its
     public_id (use the Admin API `destroy` call) — don't just
     overwrite the DB reference and leave orphaned images accumulating
     in your Cloudinary account
   - When a listing is deleted, delete all of its associated
     Cloudinary assets in the same request/transaction, not as an
     afterthought
   - Handle upload failures (network error, Cloudinary quota/rate
     limit, invalid file) gracefully — show the user a retry option
     rather than silently failing or leaving a listing half-saved
     with a missing photo

4. ACCOMMODATION SEARCH (for seekers)
   - Filter by: location (with radius search using MongoDB
     $geoNear/2dsphere on both listing and user location — e.g. "show
     listings within 5km of my saved location"), price range,
     amenities (multi-select), room type, available-from date
   - Full-text search on title/description (MongoDB text index)
   - Sort by: price asc/desc, distance, newest, most compatible
     (if the listing has occupants, sort by compatibility with them)
   - Pagination (cursor or skip/limit) for large result sets
   - Empty-state handling: if no listings match filters, suggest
     relaxing the nearest filter (e.g. "no results within 5km — try
     15km") rather than a blank page
   - Save/favorite listings for later
   - Report a listing (scam, misleading info, already taken)

5. ROOMMATE COMPATIBILITY MATCHING ALGORITHM (the core feature)
   Two-stage algorithm — HARD FILTER then WEIGHTED SCORE:

   Stage 1 — Deal-breaker filtering (hard exclusions, not scored):
     - If either user has dealBreakers.noSmokers = true and the other
       user is a smoker -> excluded entirely
     - If either has dealBreakers.noPets = true and the other hasPets
       -> excluded
     - If either has dealBreakers.sameGenderOnly = true and genders
       differ -> excluded
     - If dealBreakers.maxBudgetStrict = true and the other's budget
       range doesn't overlap at all -> excluded
     - Blocked users are always excluded both directions
   This must run BEFORE scoring — never show a percentage match for
   someone who fails a hard constraint.

   Stage 2 — Weighted compatibility score (0-100) for users who pass
   Stage 1:
     Attribute            Weight   Similarity method
     --------------------------------------------------------------
     Budget overlap         20%    overlap ratio of [budgetMin,budgetMax]
                                    ranges (0 if no overlap, 1 if
                                    identical ranges)
     Cleanliness             15%    1 - (|a-b| / 4)   (scale 1-5)
     Sleep schedule          15%    1 if same, 0.5 if one is
                                    "flexible", 0 if opposite
     Smoking compatibility   10%    1 if both non-smokers or both
                                    tolerate smoking, else scaled
                                    (already hard-filtered if
                                    dealbreaker set)
     Pets compatibility      10%    similar logic to smoking
     Noise tolerance         10%    1 - (|a-b| / 4)
     Guest frequency         10%    1 if same, 0.5 if adjacent
                                    category, 0 if opposite extremes
     Work schedule overlap    5%    1 if same category, 0.5 if
                                    compatible (e.g. remote+student),
                                    0 if conflicting (e.g. night_shift
                                    vs 9to5 in shared space)
     Location proximity       5%    1 if within preferredLocations
                                    overlap or within X km, scaled
                                    down by distance otherwise

     FinalScore = sum(weight_i * similarity_i) * 100
     (weights sum to 100%; adjust proportionally if a field is
     missing on either profile rather than assuming worst-case)

   - If a listing has multiple currentOccupants, compute the score
     against each occupant individually AND show an aggregate average,
     since a seeker might match well with 2 of 3 occupants but poorly
     with the third — show both, don't hide the disagreement
   - Confidence indicator: if either profile is missing more than 30%
     of lifestyle fields, show "Partial match — profile incomplete"
     instead of a bare percentage, so users aren't misled by a score
     computed on sparse data
   - Recompute scores whenever a user updates their lifestyle profile
     (don't cache stale scores indefinitely — recalculate on demand at
     request time rather than storing precomputed scores, since the
     user base is small enough for a final year project that live
     computation is fine)

6. CONNECTIONS & MESSAGING (spam-prevention flow)
   - A seeker cannot directly DM anyone cold — they send a
     "connection request" (optionally referencing a specific listing)
   - Recipient accepts/declines; only on accept does a message thread
     unlock (scenario: prevents the platform becoming a messaging
     free-for-all / harassment vector)
   - Either party can block the other at any time, which also
     withdraws any pending/active connection

7. TRUST & SAFETY
   - Reviews: after a connection has existed for some minimum period,
     either party can leave a rating/review of the other (past
     roommate or lister) — builds a trust signal for future matches
   - Reporting: report a user or listing (scam, harassment, fake
     listing, already-taken-but-still-listed) -> goes to an admin
     moderation queue
   - Admin can suspend users, remove listings, and view audit logs
   - Rate limiting on registration, login, and connection-request
     endpoints to reduce spam/bot signups

8. NOTIFICATIONS
   - Email (Brevo) on: new connection request, connection accepted,
     new message (digest, not per-message spam), listing about to
     expire (renew reminder), account verification, password reset

9. EDGE CASES TO EXPLICITLY HANDLE
   - User deletes their account -> anonymize their reviews/messages
     rather than breaking referential integrity (store as "Deleted
     User" rather than cascading deletes that orphan other users' data)
   - Listing's lister deletes their account -> listing auto-marked
     "removed_by_admin" or "expired", not left dangling
   - Two users somehow send each other connection requests
     simultaneously -> auto-merge into a single accepted connection
     rather than creating duplicates
   - A user's matchingStatus is "found_roommate" but they still get
     browsed via direct profile link -> show "no longer looking" state
     instead of erroring
   - Currency/localization: budgets stored and displayed in Naira
     (NGN), but store as a plain number + currency field so it's not
     hardcoded if reused elsewhere
   - Distance search when a user hasn't set their location -> fall
     back to preferredLocations text match instead of failing the
     geo query
   - Listing with zero currentOccupants -> match purely against the
     lister's own profile (normal 1-on-1 case)
